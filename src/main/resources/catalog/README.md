# Component catalog

This directory holds one markdown file per pattern, effect, or modulator, keyed by fully qualified class name (for example `heronarts.lx.audio.BandFilter.md`). It ships inside the LX jar as a classpath resource, so any consumer can resolve a component's entry at runtime with:

```java
clazz.getClassLoader().getResourceAsStream("catalog/" + clazz.getName() + ".md")
```

Third-party LX packages can ship the same layout in their own jars, keyed the same way, so a consumer walking a component's class hierarchy or package can pick up catalog entries for both stock and third-party components with one lookup convention.

## Frontmatter

Each entry starts with a small YAML-ish frontmatter block:

- `class` - fully qualified class name, must equal the filename minus `.md`.
- `kind` - one of `pattern`, `effect`, `modulator`.
- `sourceRepo` - logical name of the repo holding the source (here, `LX`).
- `sourcePath` - repo-relative path of the source file the entry was generated from.
- `sourceSha256` - sha256 of that source file at generation time. This is the staleness key: if the source changes, this hash no longer matches and the entry is stale.
- `classBytesSha256` / `classBytesOrigin` - hash of the compiled class bytes and where they came from (jar path). Optional. Lets a runtime consumer detect drift against the bytecode actually loaded, not just the source tree.
- `lxVersion` - the LX version the entry was generated against.
- `generatedAt` - timestamp of generation.
- `generator` - identifier for the tool/model that produced the entry.
- `tags` - comma-separated free-text tags.

## Body

Every entry has exactly three sections:

- `## Summary` - what the component does and its overall behavior.
- `## Parameter interactions` - how parameters affect each other or the component's behavior together.
- `## Usage tips` - practical notes for using the component well.

Parameter names, types, and ranges are deliberately left out. Those are introspectable live from the running component; this catalog exists for the behavioral semantics that aren't, especially the parts that would otherwise only be learned by reading javadoc or source.

## Maintenance contract

Entries are generated by reading the full class source, including javadoc, and defer to javadoc where the two would conflict. Freshness of this directory is the catalog maintainer's job, not the component author's: editing a pattern, effect, or modulator never obligates updating its catalog entry. `scripts/check-catalog-staleness.sh` reports stale or missing entries but always exits 0, so it never blocks a build or a contributor's PR.

Regeneration tooling (the process that reads sources, calls a model to write the Summary/Parameter interactions/Usage tips sections, and recomputes the hashes) lives in a separate repo, https://github.com/oveddan/lx-mcp. Its format contract is documented there at `docs/catalog-format.md`.
